Microsoft Entra ID to Portkey Mode A Integration

Comprehensive technical architecture, failure analysis of native Entra ID claims limitations, and the target production blueprint for an Azure-native stateless token broker utilizing asymmetric RS256 Key Vault HSM signing.

Status 2026-10-23: built and tested; this page was corrected to match

The design below was implemented as a Container App with a Key Vault signing key and Terraform (see the article README), and tested against a hybrid gateway 2.29.0. The original handoff was a design with untested code. Corrections made here:

  • The hybrid gateway reads defaults.config_slug and ignores defaults.config_id. Put the slug in the policy.
  • "Tamper-proof config" is not established. The Portkey doc says a config sent in a request header can override the token's default unless config override is disabled; that was not tested.
  • "Mode B forces one gateway per workspace" is only partly right per the doc (workspace can come from an allowlist, an org default or a sub mapping). Mode B with Entra's own JWKS was not tested.
  • Scope names must be gateway scopes (logs.read, not logs.view). usage_limits is an array in the doc; the object shape in the original sketch is wrong, and enforcement was not tested.
  • A user token for a workspace the user isn't a member of gets 403 (code 033) unless the gateway runs with JWT_JIT_USER_ACCESS=ON, which admits it as a service key and trades per-user attribution for availability.
  • The original sketch passed raw bytes to Key Vault's RS256 sign (it expects a digest), used the key name as kid (it must change with the key version), returned error messages to the caller and gave unmatched callers a default tier. The broker hashes first, uses the key version as kid, returns error codes only and refuses callers with no matching role.
  • Not tested: SaaS, key rotation, JWKS cache lifetimes, usage_limits, per-user attribution under JIT, config override by header, dead ends 1 and 2 (taken from the original handoff and Microsoft's documentation).

Executive Objective & Context

The goal of this initiative is to integrate Microsoft Entra ID as the central enterprise Identity Provider (IdP) for the Portkey AI Gateway using Portkey Mode A JWT Authentication. In Portkey’s architecture, Mode A allows the token issuer to embed rich, gateway-aware claims directly into signed JWTs. These claims dictate tenant routing, access scopes, and cryptographic guardrails before an inference request ever hits an upstream large language model.

Core Drivers: Why Mode A and config_id Are Worth It

01

Shared Gateway Density & Multi-Tenancy

A single Portkey AI Gateway cluster can support hundreds or thousands of distinct corporate workspaces concurrently. In Mode A, the token contains the dynamic portkey_workspace claim. This allows one shared gateway deployment to dynamically route traffic across the entire enterprise based on token claims alone without container replication.

02

Governance via defaults.config_slug / config_id

In Portkey, a config_id specifies model routing, fallbacks, prompt templates, and security guardrails (PII redaction, jailbreak filters). If passed via HTTP headers (x-portkey-config), clients or compromised apps can tamper with or omit the header. Putting it in a signed JWT makes it a default the client can't edit inside the token. Per the Portkey doc a config sent in a request header can still override it unless config override is disabled for the workspace (not tested here), so treat it as a default, not a lock.

3

Explored Approaches & Technical Dead Ends

Directly integrating Microsoft Entra ID as the native Mode A token issuer proved unviable due to strict schema validation rules inside Entra’s token generation pipeline. Three avenues were considered and rejected. Dead ends 1 and 2 come from the original handoff and Microsoft's documentation and were not reproduced in the lab.

Dead End 1: Entra ID Claims Mapping Policy

Rejected

Attempt: Configure an App Registration with acceptMappedClaims: true and attach a Graph claimsMappingPolicy to emit custom keys (portkey_oid, defaults).
Why it failed: Entra ID's ClaimsSchema only allows flat, primitive key-value mappings (strings, integers, booleans). It has no support for emitting nested JSON structures such as defaults: { config_id: "..." }.

Dead End 2: Entra ID Custom Claims Provider (onTokenIssuanceStart)

Rejected

Attempt: Use Entra’s custom authentication extension to invoke an Azure Function REST API during token issuance to enrich the token with complex Portkey claims.
Why it failed: The Microsoft Graph Custom Extension event schema (provideClaimsForToken) strictly validates outgoing claim payloads. Claim types are restricted to scalar primitives (string, boolean, integer) or flat collections (string[]). Nested JSON dictionaries abort token issuance with schema errors.

Dead End 3: Fallback to Portkey Mode B

Claim corrected, untested with Entra JWKS

Attempt: Use Mode B, where Portkey accepts an unmodified Entra ID token and handles workspace mapping via Gateway environment variables (ORGANISATIONS_TO_SYNC).
Why it is less attractive: Per the Portkey doc, Mode B needs one organisation per gateway, but the workspace can come from a workspace allowlist, an org default or a sub mapping, so "one gateway per workspace" is only partly right. The IdP's token can't carry defaults.config_slug, so the per-team config has to come from elsewhere. Tested: a raw Entra token sent to a gateway whose org JWKS list has no Entra key gets 401 (no matching key). Mode B with Entra's JWKS configured was not tested.

Target Architecture: Out-of-Band Token Broker & Direct Data Plane

Critical Architecture Distinction: Out-of-Band Control Plane vs. Direct Data Plane

The broker is never an in-band proxy for AI traffic. It operates strictly in the Control/Auth Plane as an out-of-band token broker. The client application calls the broker once upon boot (and refreshes every 50 minutes) to exchange its Entra token for a Mode A JWT, then caches it. All high-throughput LLM inference calls (/v1/chat/completions) travel directly from the client to the Portkey AI Gateway, with no broker in the path.

Following the principles of IETF RFC 8693 (OAuth 2.0 Token Exchange) and Portkey Mode A JWT Specification, the diagram below visualizes the decoupled workflow: the Control Plane exchanges and signs the token, Portkey fetches the broker's JWKS out-of-band, and the Data Plane delivers direct client-to-gateway inference.

Steps 1 & 2 (Entra Auth): Client authenticates via standard client credentials or OAuth authorization code flow. Entra ID returns a standard corporate JWT containing enterprise group mappings in the roles claim.
Steps 3 & 4 (Token Minting): Client calls POST /token/exchange on application boot. The broker maps roles to the Portkey workspace and defaults.config_slug, signs the token via Key Vault (RS256), and returns a Mode A JWT. Client caches this token for 50 minutes.
Step 5 (JWKS Public Key Discovery): Portkey fetches the broker's public RSA coordinates via /.well-known/jwks.json, and uses them to verify signatures (cache lifetime not measured; a newly added JWKS URL was accepted on the first request).
Steps 6 & 7 (Direct Data Plane Inference): Client makes inference requests directly to the Portkey Gateway passing the cached Mode A JWT. The broker is never in the request path. The gateway validates the JWT, applies defaults.config_slug, and routes to the upstream.

Entra ID Service Principal & App Roles Design

Key Insight: App Roles vs. Microsoft Graph Directory Queries

The token exchange broker does not need directory-reading permissions (User.Read.All, Directory.Read.All) against Microsoft Graph. Querying Graph at runtime introduces 150–300ms of network latency and risks API throttling. Furthermore, in large enterprises with over 150–200 groups, Entra ID strips the groups claim entirely due to group overage. App Roles are never omitted or stripped, making them the most reliable carrier of governance context.

Configuration Steps in Microsoft Entra ID:

  1. Register App: Create an App Registration named Portkey-Token-Broker with Application ID URI api://portkey-token-broker.
  2. Declare App Roles: Under App roles, add roles representing Portkey workspaces: Portkey.Workspace.Finance, Portkey.Workspace.HR (the lab build used Finance and HR; entra/setup.sh creates them).
  3. Assign Enterprise Groups: Under Enterprise Applications, assign existing AD security groups (e.g. "SG-FinAnalytics") to their respective App Roles. Entra emits them in the roles array (observed for both app and user tokens; group assignment needs Entra ID P1 per Microsoft).
  4. Require assignment: turn on "assignment required" so Entra refuses callers with no role before the broker sees them (observed: AADSTS501051 for apps, AADSTS50105 for users).

Azure-Native Implementation Blueprint

The implementation is a plain Node 20 HTTP service in broker/ (TypeScript, container image on Azure Container Apps, system-assigned identity with Key Vault Crypto User), not the Azure Functions v4 code of the original sketch. It exposes POST /token/exchange, GET /.well-known/jwks.json and GET /healthz. The sketch is removed from this page because it had the defects listed in the status box above; the source of truth is the repo.

Open Decisions & Implementation Next Steps

1.
Key Signing Strategy Decision:

The build signs with Key Vault on every exchange (a digest is hashed locally and signed in the vault, so the private key never leaves it). Exchange latency was not measured; the client caches the token, so inference calls don't pay it. Cached-key signing in memory remains an option if exchange latency matters.

2.
JWKS Network Reachability:

If using Portkey Cloud (SaaS), the broker's /.well-known/jwks.json route must be publicly accessible over HTTPS. The tests ran with a public endpoint and a hybrid gateway; Mode A on SaaS (control-plane validation) and a private-endpoint variant for a self-hosted gateway in AKS were not tested.

3.
Client SDK Lifecycle:

Configure client SDK wrappers (Python/TypeScript) to request a Mode A token on application boot and refresh on a 50-minute interval, storing the token in-memory across inference requests to avoid cold-start overhead.

4.
User attribution vs availability:

User tokens (with email_id) need workspace membership by default (403, code 033 otherwise). JWT_JIT_USER_ACCESS=ON removes that requirement by admitting the caller as a workspace service key. Decide whether per-user attribution matters, and check the logs: it was not verified under JIT.
